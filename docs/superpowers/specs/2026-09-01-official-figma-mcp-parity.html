Can this bridge carry the whole load?

Figma Design Relay already does things the first-party MCP server cannot — unlimited calls, live unsaved state, several files at once. This is the honest accounting of what it still cannot carry, and what it would take to close the span.

What we are comparing against

Two different first-party servers ship under the name “Figma MCP”. This spec targets the remote server, because that is the one the official Claude Code Figma plugin configures: 

{ "figma": { "type": "http", "url": "https://mcp.figma.com/mcp" } }

Its eighteen tools are the hangers on the span above, taken verbatim from the plugin's .mcp.json (figma_prod@2_2_96).

The second is the Dev Mode local server (Figma desktop app, on 127.0.0.1:3845), whose surface is a subset plus get_code and create_design_system_rules. It needs the desktop app and a Dev or Full seat, so it is not a useful baseline — and anything we match on the remote server we also match there.

Where we are already capable

These are the places the bridge already meets or beats the official server. Several of them are not incidental: they fall out of being a plugin rather than an API client.

Capability Figma Design Relay Official
Cost and rate limits Unlimited — no Figma API calls at all Rate-limited; effectively a paid-seat feature
Live editor state Reads the open document, including unsaved edits Reads Figma's server-side file state
Multi-file Registry keyed by fileKey; any number of open plugin instances One file per call, addressed by URL
Screenshots to disk save_screenshots writes straight into the workspace Inline image, or an asset URL that expires in about seven days
Export formats PNG, SVG, JPG, PDF with scale and clip Screenshots
Motion Seven tools — read, apply and remove animation styles, manual keyframe tracks, timeline duration get_motion_context, read-focused
HTML import import_html_layers bulk-imports an html-to-figma tree No equivalent
Deployment npx @gethopp/figma-design-relay; works with Figma on the web Requires Figma auth; the Dev Mode variant requires the desktop app
Transparency MIT, self-hostable, auditable Closed, hosted

The write surface is broad already: 22 mutation tools covering node properties, solid and gradient fills, effects, strokes, auto-layout, text content and typography, frames, text, shapes and images, pages, duplicate, reparent, group and ungroup, selection, viewport, and a delete that is gated behind explicit confirmation.

Where we are lacking

Ranked by how much each one blocks the sentence “use the bridge instead of the official server, every day.” The order is the argument — gap 1 carries most of the weight.

Gap 01

No arbitrary Plugin API execution

Blocking Phase 1

The official server's most important tool is use_figma: it runs arbitrary JavaScript against the Plugin API inside the file and returns whatever the script returns. Everything the Plugin API can do is reachable through it.

The bridge instead exposes a fixed menu of about forty hand-written RPCs. Anything off the menu is simply impossible. Concretely, an agent on the bridge today cannot:

  • create or edit components, component sets, variants, or component properties;
  • create or edit instances, swap main components, or set instance overrides;
  • author variables, collections or modes, or bind them to properties (setBoundVariable, setBoundVariableForPaint);
  • create or apply paint, text, effect or grid styles;
  • do boolean operations, vector editing, flatten, or outline strokes;
  • create sections or slices, or author prototyping reactions and flows;
  • set per-segment text styling (setRangeFills, setRangeFontName);
  • set constraints, layoutSizingHorizontal / layoutSizingVertical, absolute positioning, or grid layout;
  • read or write plugin data, annotations, dev resources, or export settings;
  • run node.query() or findAll, or any read the serializer omits.
Gap 02

Serialized nodes drop design-system identity

Blocking for design → code Phase 2

plugin/src/main/serializer.ts emits geometry, paints, effects, auto-layout, constraints and text properties — but omits every field an agent needs to write correct code rather than pixel-matched code:

  • componentId, mainComponent, componentProperties, variantProperties — so an instance of Button/Primary looks like an anonymous frame.
  • boundVariables — so a fill bound to color/brand/primary serializes as a raw hex, and the agent hardcodes #3B82F6 instead of reaching for the token.
  • fillStyleId, strokeStyleId, textStyleId, effectStyleId — the same problem, for styles.
  • layoutSizingHorizontal / layoutSizingVertical, layoutPositioning, layoutGrow — so hug and fill intent is lost and the agent emits fixed sizes.
  • reactions, exportSettings, annotations, absoluteRenderBounds.
Gap 03

get_design_context returns a tree, not an answer

Phase 3

Figma's version returns, in one call: React and Tailwind reference code, a screenshot, CSS-variable token names, design annotations, Code Connect snippets, and an asset URL for every icon and image. Ours returns a depth-limited JSON tree and nothing else, so the agent has to call get_screenshot and get_variable_defs separately and then invent the mapping itself.

Gap 04

No Code Connect

Phase 4

Five official tools tie Figma component keys to real codebase components. This is the mechanism that makes an agent's output use your <Button> rather than a fresh div. The bridge has none of it.

The read direction is fully reproducible offline. Code Connect mappings live in *.figma.ts files in the user's own repository, and the plugin can supply the component keys. We do not need Figma's cloud for this one — we need a parser and a lookup.

Gap 05

No cross-file or library search

Phase 5

search_design_system and get_libraries search an organisation's published libraries. The bridge sees only files where the plugin is currently open. Partly closable: the Plugin API exposes figma.teamLibrary.getAvailableLibraryVariableCollectionsAsync(), figma.variables.importVariableByKeyAsync() and figma.importComponentByKeyAsync() — but the manifest needs the teamlibrary permission, and there is no full-text component search.

Gap 06

Design files only

Phase 6

manifest.json declares "editorType": ["figma", "dev"]. FigJam and Slides files are unreachable, so get_figjam and generate_diagram have no counterpart at all.

Gap 07

Limits we cannot close

Structural

Worth stating plainly rather than pretending otherwise.

  • create_new_file is impossible. The Plugin API cannot create documents. The bridge tops out at create_page inside a file that already exists. Mitigation: document that the user creates the file and opens the plugin once.
  • The plugin must be open in the target file. The official server addresses any file the user can reach, by URL. The bridge cannot act on a pasted link to a file nobody has open. Mitigation: list_files plus an error that tells the agent exactly what to ask for.
  • No branch addressing — there is no branchKey.
  • generate_figma_design is a Figma-hosted generative model. Not replicable; import_html_layers covers an overlapping need by a different route.
  • Scripts are not atomic. Official use_figma documents that a failed script makes no changes. The Plugin API has no rollback, so a bridge script that throws halfway leaves partial mutations behind. Document it; do not paper over it.
Gap 08

No tests

Blocking Phase 1

There is no test runner, no test file, and no CI job beyond release.yml. That is about 5,200 lines of protocol-sensitive code — leader election, RPC validation, a 1,875-line plugin dispatcher — verified entirely by hand. Any plan that meaningfully grows the surface has to fix this first, which is why phase 1 opens with the harness rather than the feature.

Can the plugin sandbox actually eval?

Everything in phase 1 rests on this, so it was checked rather than assumed. The answer is yes. Figma's plugin sandbox is a Realms-based sandbox that Figma's own engineering write-up describes as implemented with with (scopeProxy) { eval(userCode) }, and which “includes a new copy of the eval function”. Community plugins that execute user-authored Plugin API code — Scripter, Figlet — rely on exactly this.

Two consequences shape the design:

  1. Use direct eval(source), never (0, eval)(source). Indirect eval runs in the realm's global scope, where figma may not resolve; a direct eval inherits the scope chain that makes it resolve.
  2. Evaluate (async () => { … }) and call the result, so a script gets both top-level await and top-level return — matching use_figma's contract exactly.

Phase 1 still probes this at runtime in a real file, so a future sandbox change fails with an actionable message rather than a bare ReferenceError.

The six phases

Each phase is independently shippable and independently useful. Phases 2 through 6 depend on phase 1 only for its test harness — but run_script makes every one of them dramatically cheaper to prototype, which is why it goes first.

Two ordering constraints are real rather than preference: phase 3 needs phase 2's resolved token and style names to generate code that references tokens, and phase 4 needs phase 2's component property definitions to author accurate mappings.

Phase Deliverable Closes Requirements
1 Test harness, then run_script — a use_figma equivalent Gap 08, Gap 01 R1–R10
2 Serializer enrichment: components, bound variables, style IDs, layout sizing, annotations Gap 02 R11–R19
3 get_design_context v2 — reference code, inline screenshot, token names and asset export in one response Gap 03 R20–R27
4 Code Connect: parse local *.figma.ts, map component keys, surface snippets in design context Gap 04 R28–R35
5 Library reach — teamlibrary permission, import-by-key, variable collections — plus whoami Gap 05 R36–R42

Phase 1 — run_script

R1–R10 · closes Gap 01 and Gap 08 · depends on nothing · planned

# Requirement
R1 The bridge exposes an MCP tool run_script taking code (string) and optional fileKey.
R2 code executes inside the plugin sandbox with the Plugin API in scope as figma, supporting top-level await and top-level return.
R3 The returned value is JSON-serialized. Figma nodes collapse to { id, name, type }; figma.mixed and any other symbol becomes "mixed"; cycles become "[circular]".
R4 Results are bounded: depth 12, 500 array items per array, 200,000 characters of JSON. Over the character cap, return a flagged truncated preview rather than an oversized frame.
R5 Scripts are capped at 100,000 characters, enforced by both the server's Zod schema and the plugin runner.
R6 A script that throws returns an MCP error carrying name: message, not a silent success.
R7 run_script is rejected in Dev Mode with the same clear message the other edit tools use.
R8 The tool description carries the non-obvious sandbox rules: return to output, load fonts before text mutation, colors are 0–1, fills are read-only arrays, await figma.setCurrentPageAsync() to switch pages, work incrementally, and scripts are not atomic.
R9 The follower-to-leader RPC path validates run_script like every other tool, via rpcInputSchemas and rpcToArgs.
R10 bun test runs in both server/ and plugin/, and is green.

Phase 2 — Serializer enrichment

R11–R19 · closes Gap 02 · depends on R10 · unlocks phases 3 and 4

Everything here lands in plugin/src/main/serializer.ts and propagates automatically to get_document, get_node, get_selection and get_design_context, which all serialize through it.

# Requirement
R11 serializeNode becomes asynchronous. manifest.json declares "documentAccess": "dynamic-page", under which the synchronous accessors this phase needs are unavailable — component identity must come from instance.getMainComponentAsync(), styles from figma.getStyleByIdAsync(), and variables from figma.variables.getVariableByIdAsync(). Every call site in plugin/src/main/code.ts awaits the new signature.
R12 INSTANCE nodes carry mainComponent: { id, key, name } plus componentProperties as a map of property name to { type, value }, so an instance of Button/Primary is recognisable as one.
R13 COMPONENT and COMPONENT_SET nodes carry key, and componentPropertyDefinitions is read only from the owning node: the node itself when it is a COMPONENT_SET, a COMPONENT only when its parent is not a set, and otherwise the variant's parent set. Reading the getter off a variant is an error the serializer must not make.
R14 Every node emits boundVariables resolved to human-readable form — { property, variableId, variableName, collectionName } — including paint-level bindings such as fills[i].boundVariables.color. A fill bound to color/brand/primary must not serialize as a bare hex.
R15 Style references are emitted with resolved names — fillStyleId, strokeStyleId, effectStyleId, gridStyleId, textStyleId, each as { id, name }. A style id of figma.mixed serializes as "mixed", matching R3.
R16 Layout intent is emitted, not just geometry: layoutSizingHorizontal, layoutSizingVertical, layoutGrow, layoutAlign, layoutPositioning, itemReverseZIndex, and the minWidth / maxWidth / minHeight / maxHeight constraints. Without these, hug and fill intent is lost and an agent emits fixed pixel sizes.
R17 reactions (prototyping triggers, actions and destinations), exportSettings, and both absoluteBoundingBox and absoluteRenderBounds are emitted.
R18 Dev Mode annotations are emitted verbatim, including their label and any pinned properties, so designer notes reach the agent.
R19 Payload discipline: every field added by R12–R18 is omitted when absent, empty, or at its default, and a regression test asserts that a plain rectangle with no component, variable, style or annotation serializes to the same shape it does today. Enrichment must not make get_document unusable on a large page.

Phase 3 — get_design_context v2

R20–R27 · closes Gap 03 · depends on R14 and R15 for token and style names

This is the tool an agent reaches for first when implementing a design, so it has to answer the whole question in one call.

# Requirement
R20 get_design_context accepts an optional nodeId. When given it serializes that subtree; when omitted it keeps today's behaviour of using the selection, falling back to the current page.
R21 The response is a multi-part MCP result: a text block carrying reference code and the token list, plus an image content block carrying the node's screenshot. Returning a base64 blob inside a text block, as get_screenshot does today, does not satisfy this.
R22 Reference-code generation lives in a pure, server-side module under server/src/codegen/ that takes the serialized tree and returns a string. It must not run inside the plugin sandbox. A format parameter selects "react" (default), "html", "css" or "json".
R23 Wherever a node carries a bound variable or a named style (R14, R15), the generated code references the token or style name, not the resolved hex or pixel value. Raw values appear only where no binding exists.
R24 Icons and images in the subtree are exported to disk under a caller-supplied directory and referenced by workspace-relative path — a deliberate divergence from the official server's ~7-day asset URLs, because local files are committable. The response must instruct the agent to reference those files rather than hand-writing <svg> markup it has no vector data for.
R25 Once phase 4 lands, hints apply in priority order: Code Connect snippet, component description, annotation, design token, raw value. The response states which source it used per node, so the agent can tell a mapped component from a guessed one.
R26 The response is bounded by the same discipline as R4 — a depth parameter, and a documented character cap with flagged truncation — so a large frame degrades rather than fails.
R27 Codegen is covered by golden-file tests: a fixture serialized tree in, an expected code string out, one fixture per format.

Phase 4 — Code Connect

R28–R35 · closes Gap 04 · depends on R13 for component property definitions

The read direction needs no Figma cloud access at all: the mappings are files in the user's own repository.

# Requirement
R28 The server discovers Code Connect files matching **/*.figma.{ts,tsx,js,jsx} under its working directory. Discovery is contained: a path resolving outside the working directory is rejected, matching the rule import_html_layers already enforces.
R29 Each figma.connect(...) call parses into a mapping record carrying the Figma file key and node id from the URL argument, the code component name, its workspace-relative import path, and its declared props mapping. A file that fails to parse is reported by path and skipped, not silently dropped.
R30 get_code_connect_map returns the mappings for a given fileKey, or for a list of nodeIds, as { nodeId, component, source, props }.
R31 add_code_connect_map writes a local file rather than calling Figma. It takes a node id, a component name and a source path, and creates or extends the appropriate *.figma.ts file. The tool description states that the mapping is a workspace file, not a cloud record.
R32 get_code_connect_suggestions proposes mappings by matching unmapped component names in the open Figma file against exported component names in the workspace, returning ranked candidates with the evidence for each match. It never writes.
R33 get_context_for_code_connect returns a component's property definitions and variant axes so a mapping can be authored accurately. Depends on R13.
R34 There is no send_code_connect_mappings equivalent. The bridge's substitute is that mappings are files under version control, and the documentation says so explicitly rather than leaving the absence unexplained.
R35 When a node in a get_design_context response has a mapping, the snippet is surfaced in that response at the priority R25 defines.

Phase 5 — Library reach and identity

R36–R42 · closes Gap 05 · depends on R10

This is the phase most constrained by what the Plugin API actually exposes, so its requirements are deliberately narrower than the official tools.

# Requirement
R36 plugin/manifest.json requests the currentuser and teamlibrary permissions. The manifest change is user-visible on plugin import, so the README explains why each is needed.
R37 whoami returns figma.currentUser as { id, name, photoUrl }. figma.currentUser can be null; the tool returns an explicit “no current user” result rather than an empty object.
R38 get_libraries returns available team library variable collections via figma.teamLibrary.getAvailableLibraryVariableCollectionsAsync(), including each collection's library name and key.
R39 Import-by-key is exposed for the four importable kinds: figma.importComponentByKeyAsync, figma.importComponentSetByKeyAsync, figma.importStyleByKeyAsync and figma.variables.importVariableByKeyAsync. Each returns the imported object's id so a following call can place or bind it.
R40 search_design_system is implemented as a narrower tool than the official one, and its description says so in the first sentence. The Plugin API has no full-text search across an organisation's published libraries, so the bridge searches what it can reach: available library variable collections, and components already present or instantiated in the connected files. The description must stop an agent assuming org-wide coverage.
R41 When a team-library call is refused because the account's plan or permissions do not allow it, the error names the permission and the plan requirement rather than surfacing a raw API error.
R42 Every tool in this phase has unit tests against stubbed figma.teamLibrary and figma.currentUser objects, so the suite runs without a Figma session.

Phase 6 — FigJam, Slides and diagrams

R43–R50 · closes Gap 06 · depends on R10

The bridge is design-file-only today because of one line in the manifest; everything downstream of changing it needs care.

# Requirement
R43 plugin/manifest.json declares "editorType": ["figma", "figjam", "slides", "dev"].
R44 The current design-editor gate (EDIT_REQUEST_TYPES plus requireEditorMode) is replaced by an editor-aware capability table. Node types and APIs differ per editor — figma.createPage() does not exist in FigJam or Slides, sticky notes and connectors exist only in FigJam, slide nodes only in Slides — and a tool unavailable in the current editor is rejected up front with a message naming the editor it needs.
R45 FigJam documents serialize STICKY, CONNECTOR, SHAPE_WITH_TEXT, CODE_BLOCK, SECTION and TABLE nodes, including connector endpoints, so a diagram's topology survives the round trip.
R46 A FigJam write surface covers creating sticky notes, connectors, shapes-with-text and sections, matching the shape of the existing design write tools — validated Zod input, fileKey routing, node ids returned.
R47 Slides support is scoped explicitly: read and screenshot are supported; write is limited to text and frame content inside existing slides. Creating slide structure is out of scope for this phase, and the documentation says so.
R48 generate_diagram accepts Mermaid source and renders it into a FigJam board. The supported subset is fixed and documented: flowchart, sequence, entity-relationship, and state diagrams.
R49 Mermaid input outside the supported subset returns an error naming the diagram type it received and listing the supported ones. It never renders a partial or approximate diagram.
R50 A regression suite proves the design-file behaviour of every existing tool is unchanged by the manifest and gate changes.

Cross-cutting

R51–R55 · applies to every tool added by any phase

# Requirement
R51 Every new tool registers a Zod schema in toolInputSchemas and a mapper in rpcToArgs, so the follower-to-leader RPC path validates it. The Record<ToolName, …> typing makes omitting the mapper a compile error; do not work around it.
R52 Every new tool accepts the optional fileKey parameter and routes through node.sendWithParams, so multi-file workflows keep working.
R53 Every new module has unit tests, and bun test stays green in both server/ and plugin/.
R54 Every new tool is added to the README's tool table, and any behaviour that diverges from the official server is called out in the Editing Notes.
R55 Errors say what to do next, not just what went wrong. “Open the plugin in the target file and retry” beats “Plugin not connected”; naming the missing permission beats surfacing the raw API error.
